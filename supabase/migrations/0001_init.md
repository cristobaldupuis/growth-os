# Phase 1 — schema discovery notes

Source of truth for the current shape: `src/services/store.js` (the
localStorage keys), populated/consumed in `src/App.jsx`'s load effect and
the `save*` helpers beside it, with the starting/demo values coming from
whichever config `src/activeConfig.js` points at (`SEED`,
`SEED_WEEKLY_METRICS` — today `src/config.csc.js`) and defaults in
`src/constants.js` (`DEFAULT_SETTINGS`, `mkDefault`).

> **Scope note.** This document was written against five state keys:
> items, settings, debates, weekly metrics and recs. The app has since
> grown five more — `KEY_CREATIVE` (creative briefs and variants),
> `KEY_PERF` (campaign-level performance rows, a genuinely different
> shape from weekly metrics — see the note in `store.js`), plus the
> `KEY_THEME`, `KEY_LIB_VIEW`, `KEY_RAIL` and `KEY_TOUR_SEEN` UI
> preferences. The last four are per-device preferences and do not belong
> in Postgres. Creative and performance rows do, and are **not** modelled
> in `0001_init.sql`. Treat this as a Phase 1 schema for the original five,
> not as a complete picture of what the app now stores.

## What's a direct mirror vs. what changed

**Direct mirror (no structural change):** initiative scalar fields, weekly
metric envelope (`date`/`brand`/`source`/`metrics`), debate transcript/results,
settings scalar fields (companyName, northStarMetric, etc).

**Changed to make it relational:**

1. **`brands` pulled out of the `settings` blob into its own table.**
   Today `settings.brands` is an array of brand-brief objects embedded in
   the settings JSON, and `initiatives.brandId` / `weeklyMetrics.brand` are
   just matching strings with no enforced relationship. Splitting brands
   into a table lets `initiatives.brand_id` and `weekly_metrics.brand` be
   real foreign keys. `brands[0]` being "the default brand" (used all over
   `constants.js`/`App.jsx` as a fallback) is preserved via a `sort_order`
   column rather than array position.

2. **`ice: {impact, certainty, ease}` flattened to three int columns**
   (`ice_impact`/`ice_certainty`/`ice_ease`) on both `initiatives` and
   `recommendations`, instead of staying nested JSON. It's a fixed, always
   3-key shape that's actively computed on (`iceScore()` in constants.js),
   so columns are more useful than a blob here.

3. **`recs` (KEY_RECS) normalized into two tables:** `recommendation_batches`
   (the batch envelope: id, generatedAt, weekOf) and `recommendations` (one
   row per recommendation, FK'd to its batch). Today it's one JSON array of
   batches each containing an array of recommendations. Splitting it out
   makes `recommendation.status` (pending/dismissed/accepted) directly
   filterable — the one place in this shape where per-item state inside a
   nested array seemed worth pulling up a level.

4. **`linkedIds` / `sourceLearningIds` kept as Postgres `text[]`,
   deliberately not turned into join tables or enforced FKs.** These are
   soft references to `initiatives.id` — in the seed data (the active
   `config.*.js`) they sometimes point at ids that get pruned or
   reordered, and the app
   never treats a dangling reference as an error (see `linkedIds` usage in
   `App.jsx`/`portfolio.js`, which just filters). A hard FK would make
   demo-data edits brittle for no real benefit in a read-only layer.

**Left as JSONB (deliberately not normalized):**

- `initiatives.results` / `initiatives.prediction_snapshot` — optional,
  variable-shape objects (results depends on what the team fills in at
  close; snapshot is a point-in-time freeze). No other table needs to
  join against their fields.
- `weekly_metrics.metrics` — key set varies by `source` (manual vs. Meta vs.
  GA4 vs. Google Ads each have a different field list, see
  `METRIC_SOURCES` in `constants.js`). Pivoting to columns would produce a
  very sparse table for a read-only demo.
- `settings.agents` / `settings.health_metrics` / `settings.data_sources` /
  `settings.categories` — config lists iterated by the frontend, not
  queried relationally by anything else.
- `debates.transcript` / `debates.results` — AI-generated, display-only
  blobs (chat turns; synthesized initiative ideas).

## Explicitly not carried over

- Nothing from the demo-only `gos_last_backup` localStorage timestamp
  (backup-nudge bookkeeping, not app state).
- No `client_id`/`tenant_id` column anywhere — this schema assumes one
  Supabase project per client, per the existing config-first deployment
  model in DECISIONS.md ("Config-first per-client deployment: no
  multi-tenant auth"). If that decision changes, every table here would
  need a tenant column and RLS policies added — flagging it now so it's
  not a silent gap.
